# Add your own functions

Need your guests to call something the platform doesn't provide — a database client, an
internal API, a signing routine? Add a **custom bridge**: a native function *your app*
defines once (in Rust, the host language) and calls from **any** guest — TypeScript, Rust, or
Go — as an ordinary typed import. It's RUSM's answer to a wasmCloud **capability provider**,
but compiled-in and typed: no lattice, no broker, no RPC, no JSON dispatcher, and the same
cost as a built-in. The example below — a `weather` function — is live in all three guest
languages.

## 1 — Define the bridge

A bridge is a directory `bridges/<name>/` with two files: the **contract** (`bridge.wit`, the
app's own WIT package) and the **host impl** (`host.rs`):

```wit
// bridges/weather/bridge.wit — the app's own WIT package
package weather:bridge@0.1.0;

interface forecast {
    lookup: func(city: string) -> string;
}
```

```rust
// bridges/weather/host.rs — the native impl. The ONLY Rust an app must add for a
// native capability; its guests stay in any language. `rusm build` generates the
// surrounding glue (src/bindings.rs, src/bridges.rs, wit/).
use crate::bindings::weather::bridge::forecast;
use rusm_wasm::wasmtime::component::HasSelf;
use rusm_wasm::{wasmtime, BridgeHost, BridgeLinker};

pub fn add_to_linker(linker: &mut BridgeLinker) -> wasmtime::Result<()> {
    forecast::add_to_linker::<_, HasSelf<BridgeHost>>(linker, |host| host)
}

impl forecast::Host for BridgeHost {
    async fn lookup(&mut self, city: String) -> String {
        // Reaches real host state through BridgeHost (here the caller's pid); a real
        // bridge would call a service via self.runtime() and gate on self.caps().
        format!("sunny in {city} (served by pid {})", self.pid())
    }
}
```

## 2 — Grant it (default-deny)

A bridge is reachable only by a component whose capability profile lists it — like every
other grant, default-deny:

```toml
[capabilities.forecaster]
inherits = "sandboxed"
bridges = ["weather"]        # this profile may import the `weather` bridge

[components.api]
capability = "forecaster"
```

## 3 — Call it from a guest

A guest calls the bridge as a plain typed import — no dispatcher, no marshaling (Rust/Go get
native types; TS is typed by a generated `bridges.d.ts`):

::: code-group

```ts [TypeScript]
/// <reference path="../../bridges.d.ts" />
import { websocket } from "rusm-ts";

// `weather` is a typed global the per-app js-runner exposes (rusm build compiles it in).
export default websocket({
  message(socket, data) {
    const city = new TextDecoder().decode(data).trim();
    socket.sendText(weather.lookup(city));
  },
});
```

```rust [Rust]
// The `bridge = …` attribute imports the bridge; call it at `crate::<iface>`.
use rusm_rs::http::{Params, Request, Response};

#[rusm_rs::handlers(bridge = "weather:bridge/forecast@0.1.0")]
pub mod api {
    use super::*;
    pub fn forecast(_req: Request, p: Params) -> Response {
        Response::text(crate::forecast::lookup(p.get("city").unwrap_or("nowhere")))
    }
}
```

```go [Go]
import (
	"github.com/archan937/rusm/packages/rusm-go/web"
	forecast "go-api/internal/wit/weather/bridge/forecast" // generated by rusm build
)

func run() {
	h := web.NewHandlers()
	h.Handle("forecast", func(_ web.Request, p web.Params) web.Response {
		return web.Text(forecast.Lookup(p.Get("city")))
	})
	h.Serve()
}
```

:::

## Rich types, not just strings

A bridge carries the **full WIT value-type set** — records, variants, enums, lists, options,
results, tuples — identically for all three guests. Add a structured call:

```wit
record query { city: string, units: units }
enum units { celsius, fahrenheit }
record report { city: string, sky: sky, temp: s32 }
enum sky { sunny, cloudy, rainy }

detailed: func(query: query) -> report;
```

Rust and Go get the native generated types (`forecast::detailed(&Query { … })`); TypeScript
gets `weather.detailed({ city, units: "Celsius" })` fully typed (records → interfaces, enums
→ string unions), marshaled JS↔Rust over `serde_json` — but the *host call itself stays a
typed WIT call*, never a generic dispatcher.

## How it builds

`rusm build` discovers `bridges/`, generates the host glue + the per-guest bindings, vendors
the contract into each granted component, and compiles the components **plus a small host
binary** that registers the bridges. `rusm serve` runs that host binary — the same serve loop
as a pure-guest app, with your bridges wired in. **`rusm new <name> --bridges`** scaffolds the
whole thing. See the runnable
[`custom-bridge`](https://github.com/archan937/rusm/tree/main/examples/custom-bridge) example
(the `weather` bridge, called from Rust, Go, and TypeScript guests).

## The platform / application split

The host impl is Rust because the host **is** Rust (`rusm-wasm` / Wasmtime) — there is no
other language a host function can be. That one file is the only Rust an app adds for a native
capability; its **guests stay in any language**, calling the bridge as an ordinary typed
import. That is the whole point: a wasmCloud-style provider, minus the lattice, the RPC, and
the marshaling — just a compiled-in, capability-gated, typed host call.
